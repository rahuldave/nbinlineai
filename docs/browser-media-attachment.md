# Attach an image to an AI question

`attach_media(media, question_cell_id, detail="auto")` proposes one exact still image for one identified AI question. It accepts an owned memory result with a `media_id` or a saved-file reference with its server-root-relative `path` and SHA-256. A visible preview asks you to confirm the image and names the target question. Clicking **Attach image** records the image reference and hash on that question; it does not run the question or call a model. If that question already has an image, the confirmation explicitly says it will replace it. Cancel leaves the earlier attachment in place.

```python
from nbinlineai.tools import attach_media
attached = attach_media(image_result.media, question_cell_id="your-question-cell-id")
```

The Python call returns a `BrowserReceipt` promptly. In a later cell, inspect `attached.status`, `attached.result`, and `attached.error`. A waiting receipt becomes `completed` after the visible confirmation, or `cancelled` or `failed` if you decline or the image is unavailable. You can discover the target question's actual cell ID with `list_cells`; do not use a displayed index in place of an ID. The [disposable notebook example](https://github.com/rahuldave/nbinlineai/blob/main/examples/browser-media-attachment.ipynb) creates a tiny PNG and its actual hash, demonstrates the labeled call and later receipt inspection, and removes the temporary file after the question.

After confirmation, that question shows a small **Image attached** notice with **Remove image**. Removing clears only that question's image reference; it does not delete a saved file or the original managed media. The next confirmation can replace a prior image, and a temporary image that expired can be removed and attached again. A temporary grant may expire when its media, browser tab, or kernel ends. There are at most four outstanding temporary grants per question, eight per browser owner, and 256 on the server; confirming the same exact image, detail, and question again reuses its grant.

Only the confirmed question sends the image when you deliberately run it. Earlier questions' attachments do not carry over to a new question. Context preview verifies the saved file and selected model and includes the actual image representation in the 64,000-character host submission estimate; opening a preview does not attach, change, or execute anything. Each actual model round rechecks the question, backend support, exact bytes and hash. A modified or missing saved file fails instead of silently sending different pixels. An in-memory image expires with its owned media result, tab, or kernel; its opaque grant in notebook metadata does not make it survive reopening. Save the media first if the question must work after reopening. A saved confirmation retains the exact path, hash, question ID and detail in notebook metadata; it can be verified again from the same authenticated Jupyter project after reopening. Neither pixels nor browser-owner credentials are stored there.

PNG, JPEG, WebP, and single-frame GIF are supported, within the existing 4,096-pixel side and 16-megapixel still-image limits. SVG, audio, animated GIF and full video are refused for model input. Capturing or previewing media alone never sends it to a model. The offered OpenAI API and Anthropic API models use genuine native image content. OpenAI API accepts `auto`, `low`, or `high` detail; Anthropic accepts `auto` only because its native image part has no equivalent generic detail setting. The ChatGPT subscription connection uses a private native local-image item and accepts all three detail choices. An unknown or text-only model fails with `provider_unsupported`; select a supported model explicitly. If the exact image plus question and tool schemas exceed the submission budget, create and confirm an explicit smaller derivative. The extension never resizes an accepted image behind your back.

This is source-only behavior on the browser/media implementation branch. The published PyPI 0.1.15 package is unchanged. The example can be prepared without a provider call; running its AI question uses your selected connection and may incur normal API usage. Provider payloads are covered by deterministic offline fixtures; the real JupyterLab attachment interaction still needs its isolated browser check. Real camera or phone permissions are separate manual checks.

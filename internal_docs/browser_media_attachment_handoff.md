# Browser media attachment implementation handoff

**Implementation topic:** `codex/browser-media-attachment`, rooted in reviewed foundation `c876fd4c77517c08b60670a0ecc66029872b02b3` with the later source normalization checkpoint `dbfce3466e4aec0814eb0e28a8e85a29e2e5fd28`. Approved contract: `internal_docs/browser_media_tool_spec.md` at main `61fa3fe517999d8f88ff328a99fc86a34dfb470b` and selected prompt `e3fcf33b20ec10cd511129cd1672b98d307e4a5c`. This branch is implementation work, not a PyPI release.

`attach_media` is a direct execution-bound browser receipt and a named model-facing special action. Both routes normalize a rich receipt descriptor to an exact `MediaRef` before operation creation. `src/browserMediaAttachment.ts` is registered explicitly from plugin startup; it binds the original notebook model/kernel and question ID, reads exact bytes through the authenticated browser media client, compares the SHA-256, shows a compact visible image preview and replacement notice, and refuses a running or changed question. It rechecks after the final asynchronous status read immediately before updating metadata. User confirmation stores only a versioned compact reference in that question's shared metadata, preserving unrelated fields; it never executes the question. Cancel and failed transition restore earlier attachment metadata. A question-local indicator provides explicit removal. The backend `MediaRegistry` owns at most 256 outstanding grants globally, 8 per owner, and 4 per question; exact owner/question/media/hash/detail confirmation reuses its grant. A newly minted memory grant becomes usable for model input only after its attachment operation completes; cancellation, failure, and expiry prune uncommitted grants without revoking successful grants reused by another attempt. Terminal confirmation requests cannot replay a cached grant. The internal revoke command checks owner and question and clears a removed or replaced grant without deleting source media. An in-memory grant is owner/question/media/hash/detail bound and removed on media release, owner loss or expiry. Saved metadata keeps path/hash/question/detail and uses a new live owner proof on reopen; every preview and actual round rereads from the anchored server root and checks SHA-256 and still-image pixels. Prepared image bytes remain accounted for until preview completion or the entire provider stream ends, including cancellation; a failed validation releases the reservation promptly. No owner secret or pixels enter metadata, tool text or logs.

`nbinlineai/model_image.py` mirrors pinned FastLLM 0.0.63 native converters for OpenAI Responses and Anthropic. The genuine `InputImage` is present only in the current question's provider message; its data URL and tool schemas are included in the exact per-submission JSON character estimate before optional context. OpenAI low/high uses FastLLM's existing `xtra_body` input override so the same provider HTTP/stream/auth path receives a native `input_image.detail`; Anthropic has no generic detail and rejects non-auto. The existing 64,000-character host estimate rejects oversized exact inputs, asking for an explicit smaller derivative. No tool effects replay during budgeting. The seven offered API model IDs carry explicit image capability; unknown/custom models fail closed.

For ChatGPT subscription, `inputModalities` is read from the pinned App Server catalog. An absent field uses the documented text/image compatibility default only after the model has passed both the bundled catalog and `SUPPORTED_MODELS` checks; invalid, empty or text-only fields do not allow image input. The private runtime serializer keeps ordinary `_round_text` text-only and adds a distinct native `localImage` item pointing to a mode-0600 exact-hash temporary file inside the private round directory. The file lasts through the model turn and is removed on completion, failure or cancellation. Round preview reserves a 1,024-character path plus bounded RPC metadata and actual `turn/start` serialization is rechecked before sending. Native `view_image` remains disabled.

Source basis checked on 2026-09-28: [OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision) documents Responses `input_image.detail` (`auto`, `low`, `high`); [OpenAI gpt-6-sol](https://developers.openai.com/api/docs/models/gpt-6-sol), [gpt-6-luna](https://developers.openai.com/api/docs/models/gpt-6-luna), and [gpt-6-astra](https://developers.openai.com/api/docs/models/gpt-6-astra) list image input. [Anthropic model overview](https://platform.claude.com/docs/en/models/overview) lists image input for the four configured Claude choices, and [Anthropic vision](https://platform.claude.com/docs/en/build-with-claude/vision) describes native base64 image sources. [ChatGPT App Server models](https://learn.chatgpt.com/docs/app-server) documents the absent `inputModalities` fallback; pinned `openai-codex` 0.156.1 generated types include `localImage` with detail. These are capability claims for the offered choices, not permission to infer custom models.

Verification uses isolated registry, HTTP, converter, prompt and fake App Server fixtures; no paid provider call. The example is `examples/browser-media-attachment.ipynb`.

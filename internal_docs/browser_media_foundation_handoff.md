# Browser media foundation implementation handoff

**Implemented on topic `codex/browser-media-foundation` from main `61fa3fe517999d8f88ff328a99fc86a34dfb470b`; not released.** Normative API: main `internal_docs/browser_media_tool_spec.md` at the same revision. Task prompt selected from `e3fcf33b20ec10cd511129cd1672b98d307e4a5c`.

The server registry is `nbinlineai/browser_media.py`, exposed through authenticated JSON and raw binary routes in `nbinlineai/handlers.py`. Browser ownership includes session, current kernel, live model ID, client ID, and a server-minted secret held in tab memory. Each create/save request freezes the authenticated session path at request start for `save_to="auto"`; renaming the notebook changes later requests but never retargets an existing one. Current session/kernel are rechecked on every route. Operations are idempotent by owner/request ID and exact canonical arguments. Binary uploads use a separate channel and descriptor hashes; direct Python receipts receive binary comm buffers and validate descriptor length/hash before decoding Pillow stills or `MediaClip` values. Model tools receive bounded JSON descriptors.

Initial constants: 30-second heartbeat, 90-second owner lease, 120-second permission deadline, 5-minute final-status retention, 10-minute media idle expiry, 100 MiB encoded media per notebook, 256 MiB combined stored/staged/in-flight cap, 50 MiB upload cap, 4096-side/16 MP still cap, 12 batch items/32 MP aggregate decoded pixels, 60 seconds/16 MiB in-memory clip and 300 seconds/50 MiB saved clip caps. A server periodic callback sweeps expired records every 30 seconds. Status reads do not renew media; binary fetch and explicit save do. Saved files use an anchored filesystem walk, a temporary file, and a no-overwrite hard link; rollback retains the original directory descriptor and checks the created inode. In-memory operations work without a filesystem Contents root, while save reports unsupported there. Streaming ingress checks authorization and owner/operation admission before any body chunk, caps per-request and aggregate bytes, and releases aborted reservations.
Capability facts are limited to 2,500 JSON characters. Every registered operation has a compact availability boolean; `omitted_details` counts optional reasons or formats left out to preserve the 4,000-character model action envelope when all families register. Registration is capped at 48 operation names of at most 40 characters.

TypeScript registration is `registerBrowserOperation(name, handler, capability)` in `src/browserMediaClient.ts`; registered handlers automatically enter the shared model action dispatch through `hasBrowserOperation` and `context.start`, returning an immediate bounded operation descriptor that outlives the prompt. A family handler receives a fixed `BrowserOperationContext` and can create, transition, upload, fetch, cancel, register operation cleanup, and obtain an abort signal. `registerSource`/`endSource` scope up to 16 live sources to that context; a canvas invalidation calls `endSource(id, 'source_ended')` and the one recorder implementation handles finalization. `beginBatch`/`upload(..., batchIndex)`/`finishBatch` atomically expose a completed multi-media result; descriptors page below the model action limit, while a direct Python receipt receives all verified binary buffers as typed results. `fetchReference` resolves an owned memory media ID or exact saved path/hash. `src/browserMediaComm.ts` binds Python requests to the exact outgoing execute request and notebook model. `src/browserMediaStatus.ts` exposes pending/completed state and Stop in the notebook header. The recorder family owns the one recorder implementation; the playback family owns the decoder interface used by transformations. Neither exists in this foundation topic yet.

Focused server tests are in `tests/test_browser_media.py` and `tests/test_browser_media_handlers.py`; the isolated browser fixture is in `tests/e2e/browser-media-foundation.spec.ts` and registers a test-only 2×2 PNG operation only when the disposable 8897 server advertises its explicit E2E mode. The public example uses an exact local PNG file reference and no private capture API. The server fixture refuses 8888 and uses temporary notebooks/config. Run a frontend build and relink before browser tests, never concurrently with another browser run. No live provider or hardware capture was used. The current topic still requires independent review and PR/CI before integration; PyPI is unchanged.

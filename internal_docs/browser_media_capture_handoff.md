# Browser capture and shared recorder handoff

**Historical implementation topic `codex/browser-media-capture`, based on reviewed foundation `c876fd4c77517c08b60670a0ecc66029872b02b3`; its source merged through PR #31 (`11eae2b`), but is not in published PyPI 0.1.15.** The approved API is `internal_docs/browser_media_tool_spec.md` at main `61fa3fe517999d8f88ff328a99fc86a34dfb470b` and the selected task prompt is at `e3fcf33b20ec10cd511129cd1672b98d307e4a5c`.

The shared source hook is `recordingSourceEnded(context, sourceId, reason, cleanup?)` from `src/browserMediaRecorder.ts`. A camera, microphone, screen, or canvas family calls it from the `onEnded` passed to `context.registerSource`; the optional cleanup callback runs even when a recording flush fails. The source's returned `sourceId` can be captured in that callback. `source_ended` flushes the selected recording destination once; `cancelled` discards unfinished data. `stopRecordingHandle` and repeated source-end callbacks share one finalization promise. Explicit sources survive a normal recording stop; convenience operations own and stop their tracks. Encoder error or unsolicited recorder stop transitions to failed promptly; admission rechecks cancellation, owner, operation and live tracks before starting the recorder.

`MediaRegistry.claim_recording(owner, operation_id, session_paths)` admits one recorder for the server's current canonical notebook path across clients and distinct Jupyter sessions. The authenticated handler serializes claim requests and refreshes the current paths of all active claimants from the session manager before each admission. The claim retains its exact owner and operation ID for release; a notebook rename updates admission identity without changing the operation's frozen save destination. Matching terminal transition, upload completion/failure, cancel, or owner expiry releases only that claim. Slow encoding and saving remain outside the admission lock. Registry and authenticated HTTP regressions cover same-path sessions, rename, distinct documents, and stale-owner cleanup.

The public direct and model-facing capture names live in `nbinlineai/browser_capture_tools.py`; `camera` declares twelve names and `screen` declares four. `capture_tool` is an opt-in alias, excluded from the default screen group. The frontend registration is in `src/browserMediaCapture.ts`, with one shared MediaRecorder in `src/browserMediaRecorder.ts`. The source contract above is the hook needed by the canvas family. Recording MIME and explicit extension validation are shared server rules in `nbinlineai/browser_media.py`; encoded uploads use the authenticated foundation binary route. `start_share` only prepares a visible button: `getDisplayMedia` is called synchronously inside its click handler, not during a model or Python call. Requested-but-missing display audio requires a second explicit silent-share click.

`src/browserMediaCaptureResults.ts` uses the shared `browserMediaResultBudget` estimate of Python's ASCII-escaped JSON encoding before a result reaches the registry's 1,500-character transition cap. Device pages retain exact IDs, shorten only display labels when necessary, and expose `labels_truncated`/`omitted_count`; source settings omit an oversized browser device ID with `device_id_omitted` instead of returning an unusable partial ID. Focused tests cross-check emitted pages and settings with Python `json.dumps`.

The user-facing contract and all seventeen examples are in `docs/browser-media-capture.md` and `examples/browser-media-capture.ipynb`. Every API has stable IDs `capture-<tool>-heading`, `capture-<tool>-call`, and `capture-<tool>-inspect`; browser-only calls/inspections are tagged `nbinlineai-ui-only`. The notebook uses `save_to=None` to avoid generating user files and has an explicit microphone cleanup cell. At integrated source head `e5ba74f2c38f0e66c6cc7aec9ac43916929b5367`, the exact copied public notebook runner and five focused capture cases passed after a fresh frontend build/relink in isolated Chromium/JupyterLab with real kernels and deterministic devices. Physical camera, microphone and screen hardware remain untested. This source topic has not been released to PyPI.

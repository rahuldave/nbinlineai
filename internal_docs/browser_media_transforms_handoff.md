# Browser media transformations implementation handoff

Status: GROUP5 implementation topic based on playback `e7351ad001d7716dffeb223670c14c5c394e0f4c`, normalized foundation `dbfce34`, and playback catalog `262d244`; not released to PyPI. Approved prework is main `61fa3fe517999d8f88ff328a99fc86a34dfb470b`, selected prompt `e3fcf33b20ec10cd511129cd1672b98d307e4a5c`. PR target is main; foundation and playback are prerequisites. This document describes this implementation branch only.

`nbinlineai/browser_transform_tools.py` exposes the three public, nonblocking receipt calls. `src/browserMediaTransforms.ts` registers them explicitly at frontend startup; the module uses the shared playback decoder/AbortSignal/pixel budget, hashes the output, and uploads new PNGs through the foundation transport. `extract_frames` uses the same verified video lease and its `frameAt` seeking method, one frame at a time. It records actual seconds per part. `crop_image` and `annotate_image` never mutate their source, and redaction paints opaque black pixels. Annotation shapes and numeric limits are validated at both Python/model and browser boundaries. There is no new decoder, recorder or byte store.

The isolated storage checkpoint `ba9c58f49dfebc0c29f3d6c5a2bf4ffa67b6d16b` was cherry-picked into this topic as `8794673`. It validates derivative metadata against each frozen operation and exact source hash, retains actual timestamps in paginated descriptors, and uses the existing anchored exclusive writer for saved-only JSON sidecars. The narrow deferred HTTP upload save route uses that same transaction. All media/sidecars created by a failed batch are rolled back. Memory-only derivatives have no sidecar. `save_media` on a retained memory derivative writes the sidecar when it deliberately creates a new file. Generic batch fixture tests were renamed to `fixture_batch` so production `extract_frames` operations must carry the provenance contract.

The notebook `examples/browser-media-transforms.ipynb` generates a deterministic 64×64 PNG and a self-contained 16×16 two-color VP9 WebM clip. The video payload was generated from red and blue one-second color sources at 2 fps with ffmpeg/libvpx-vp9; encoded SHA-256 is `2fa8278237cca670f10f326a972d9e0669be28b75b44514fabf034cbefb0575d`. It has one heading plus `transform-{frames,crop,annotate}-call` and later `-inspect` cells per tool. The setup and cleanup run headlessly; six browser-dependent cells are tagged `nbinlineai-ui-only` and explicitly enumerated by `tests/test_examples.py`.

Focused checks: 63 combined Python wrapper, storage, registry/HTTP and headless notebook tests; nine decoder/transform frontend tests; TypeScript no-emit and Ruff. The exact public notebook passed in isolated JupyterLab/Python kernel on Playwright Chromium and WebKit: the 16×16 VP9 clip decoded red and blue frames at the requested positions, with `requestVideoFrameCallback` presentation times carried in descriptors; saved crop and JSON sidecar plus opaque redaction and unchanged source pixels passed. WebKit returned an RGBA Pillow image where Chromium returned RGB, so the notebook compares color channels while retaining the exact pixel-color assertions. The pinned headless Firefox browser reported `unsupported` for this VP9 clip, then completed the exact notebook's PNG crop, sidecar, annotation, and cleanup; it does not establish actual Firefox video decoding. The first WebKit implementation registered the frame callback after `seeked` and timed out intermittently; the tested repair registers before seeking and joins frame presentation with seek completion. No real hardware, paid provider, personal media, mobile browser, branded Edge or Safari has been exercised. This source commit and any PR merge do not publish PyPI or deploy docs.

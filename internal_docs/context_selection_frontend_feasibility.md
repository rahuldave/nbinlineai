# Context selection controls: frontend feasibility

Research date: 2026-09-23. This is a design handoff, **not an implemented feature**. Local API evidence is from the installed JupyterLab 4.6.4 source in `node_modules`; `ai-jup` was checked at [commit `2ac432b`](https://github.com/AnswerDotAI/ai-jup/tree/2ac432b6c7662da0e894272831be9f7f18182901). The broader data-flow and future-mode questions are in [cell, kernel, and context selection](cell_kernel_model_and_context_selection.md). The [next-feature brief](context_selection_next_feature.md) resolves the recommended product semantics; alternatives discussed below are research, not shipped behavior.

## Verified current capabilities

- The extension already has an `INotebookTracker` setup for each `NotebookPanel`, adds a notebook-wide defaults row through `panel.contentHeader`, observes notebook cell changes, and decorates visible prompt/answer widgets. The current `decorate` function appends prompt controls to `widget.node`, including persistent `metadata.nbinlineai` changes, and tears its DOM observer down with the panel. See [`src/index.ts` lines 1093-1165](../src/index.ts#L1093-L1165) and [lines 1219-1253](../src/index.ts#L1219-L1253). There is no current context-mode selector or include flag.
- `INotebookModel.cells` is an ordered `CellList` of `ICellModel`s; each model exposes a stable `id`, `type`, `sharedModel` source, `getMetadata`, `setMetadata`, and `metadataChanged`. Notebook metadata has equivalent methods and a change signal. These APIs permit durable per-cell and notebook settings without depending on rendered cells. See [JupyterLab 4.6.4 cell model](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cells/src/model.ts#L46-L121) and [notebook model](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/notebook/src/model.ts#L23-L99).
- `src/context.ts` already walks **cell models**, not DOM widgets, stopping at the current AI prompt ID. It sends all earlier code, Markdown, and raw cells with current in-memory source and metadata, including offscreen/unsaved edits. The current request calls this immediately before creating/reusing the answer. See [`src/context.ts` lines 13-30](../src/context.ts#L13-L30) and [`src/index.ts` lines 667-704](../src/index.ts#L667-L704).
- JupyterLab creates `Cell` widgets for code, Markdown, and raw models and exposes them as `notebook.widgets`. A cell exposes `inViewportChanged`, and the notebook forwards `cellInViewportChanged`; the signals fire around DOM attach/detach. `Notebook.modelChanged` and `cells.changed` cover replacement/add/remove. See [JupyterLab 4.6.4 notebook viewport signal](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/notebook/src/widget.ts#L257-L265), [widget access](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/notebook/src/widget.ts#L330-L333), [cell creation and signal connection](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/notebook/src/widget.ts#L690-L711), [signal forwarding](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/notebook/src/widget.ts#L946-L952), and [cell viewport state](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cells/src/widget.ts#L235-L265). Windowing can detach a widget node; a checkbox in that node is presentation only, not the source of truth.
- A supported **Cell toolbar registry does exist**: `IToolbarWidgetRegistry.addFactory('Cell', itemName, factory)` in `@jupyterlab/apputils`, combined with a `jupyter.lab.toolbars.Cell` schema contribution. Verified in [JupyterLab 4.2](https://github.com/jupyterlab/jupyterlab/blob/v4.2.0/packages/apputils/src/tokens.ts#L1543-L1573) and [4.6.4](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/apputils/src/tokens.ts#L2060-L2102). The separate [cell-toolbar extension](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cell-toolbar-extension/src/index.ts#L638-L686) wires it to notebook widgets. However, the built-in toolbar belongs to the **active cell**, can hide for lack of room/hidden input, and can be disabled. Its [tracker behavior](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cell-toolbar/src/celltoolbartracker.ts#L1562-L1592) makes it suitable for an active-cell shortcut, not a persistent checkbox on every visible cell. No compatibility floor change is needed for that registry.
- `Cell.IContentFactory.createCellHeader()` and `ICellHeader` are also public, but installing a different content factory just for a checkbox is broader than necessary. See [cell initialization](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cells/src/widget.ts#L589-L605) and [header/footer interfaces](https://github.com/jupyterlab/jupyterlab/blob/v4.6.4/packages/cells/src/headerfooter.ts#L19-L43). A lightweight control on each public `Cell.node` follows the extension's existing decoration pattern.
- The server presently forms completed AI prompt/answer **pairs** as atomic history units and ordinary code/Markdown as source units, then chooses nearest first within a character budget. It discovers inherited `&` tools from all preceding ordinary Markdown and AI questions before text trimming. See [`context_budget.py`](../nbinlineai/context_budget.py#L58-L79), [`build_context`](../nbinlineai/context_budget.py#L133-L220), and [`prompt.py` inherited tools](../nbinlineai/prompt.py#L100-L145). A frontend-only filter would be insufficient for later-cell modes, pair handling, and tool eligibility.

## Recommended frontend integration

Use a small, accessible **Include in AI context** checkbox on every cell widget (code, ordinary Markdown, AI question, AI answer; raw cells need an explicit product decision). Attach it to `widget.node` with a stable `data-nbinlineai-context-include` selector and an `aria-label` including cell type and ID or position. This follows the extension's existing prompt-control pattern and uses public `Cell`/`Widget.node` APIs, without replacing the notebook content factory. Keep the control visually outside editable/rich Markdown content so it never enters cell source, code output, or AI context. A small chip in a cell's top edge is likely less disruptive than a full toolbar row. The public header factory is an alternative only if a future notebook factory integration is justified.

Store selections in notebook/cell **model metadata**, not checkbox DOM state. The [feature brief](context_selection_next_feature.md) recommends notebook `nbinlineai.defaults.contextMode`, explicit cell `nbinlineai.contextInclude` choices, and a Custom initialization flag. Computed preview checks remain transient. Merge metadata rather than replacing AI flags or unrelated fields; moves preserve choices and opening/rendering/previewing does not dirty the notebook.

Use the existing notebook defaults row for **Default, Full notebook, All above, 10 above, 10 above + below, Custom**, with an explicit preview target question. Clicking another cell's checkbox must retain that target. Default preserves 0.1.7 nearest-above behavior and needs an authoritative backend preview to show which cells fit: current context reports only provide counts, and the frontend does not know live schema/interpolation cost. Explicit modes show selected candidates and distinct budget-omitted/partial indicators. Full notebook remains bounded. Switching a computed checkbox initializes Custom from the displayed selection; see the brief for persistence and new-cell behavior.

### AI question/answer policy

0.1.7 represents completed AI pairs as atomic history units. Two implementation options were considered: link both cells' checkboxes to preserve whole turns, or allow independent selection and define a source representation for a selected half. The **feature brief recommends independent selection**, matching the requested per-cell control. Both selected cells wholly above can remain prior history; a selected question/complete answer alone, or selected later AI material, becomes explicitly labeled notebook source, never a fabricated prior assistant exchange. Current question and every linked current answer are always excluded from optional context; failed/running/cancelled/orphaned answers remain ineligible. This is a deliberate backend change, not a frontend checkbox alone.

### Lifecycle and performance

Build selection from `INotebookModel.cells` at execution time. Decorate widgets on `cellInViewportChanged` and on initial panel setup; handle model/cell list changes and metadata edits; remove listeners on panel disposal. Do not use DOM order or `activeCellIndex` as the saved identity. A `WeakMap<Cell, control>` or idempotent `querySelector` avoids duplicate boxes after viewport reattachment. One delegated `change` listener on `panel.content.node` can avoid thousands of handlers; if individual model `metadataChanged` connections are added, disconnect them when models are removed/replaced and the panel closes. The present full `decorate(panel)` scans all widgets and should not be triggered on every checkbox hover/scroll in a 10,000-cell notebook. Update only the affected visible widget, with a separate model-level snapshot calculation. Use JupyterLab theme variables and a hit target that works in both edit and command modes; checkbox clicks must not inadvertently run or select a cell.

## Mode and backend handoff

For **All above** and **10 above**, select physical model indices before the current prompt. For **10 above + below**, take ten physical cells on each side while excluding the current prompt and its linked answer. `Full notebook` can enumerate every model, including offscreen cells. `Custom` uses stable selected IDs rather than a one-time index. These are candidate scopes; the nearest-first budget needs a defined distance/order priority when *below* cells are admitted. The current `preceding_cells` field and system instruction explicitly mean “above,” so sending later cells under that name would mislabel them. Later AI turns must not masquerade as earlier chat history; they need exclusion or a separately labeled source representation. Raw cells, empty cells, unpaired AI cells, and tool declarations each need an eligibility rule and accurate selected/omitted counts.

The feature brief deliberately preserves **tool inheritance independently of prose selection**. Unchecking an earlier declaration cell does not revoke its tools, and below-cell declarations are not newly registered by wider context modes. This matches the prior release's explicit user requirement; show inherited tools separately and document what the context checkboxes control. A future per-tool permission interface is separate scope. Current-question `$` interpolation remains unchanged. Server reports must distinguish selection exclusion, ineligibility and budget trimming, with stable IDs for accurate checkbox previews.

## `ai-jup` comparison

No context-include checkbox or mode dropdown appears in the [inspected `ai-jup` frontend source](https://github.com/AnswerDotAI/ai-jup/tree/2ac432b6c7662da0e894272831be9f7f18182901/src). Its [`_gatherContext`](https://github.com/AnswerDotAI/ai-jup/blob/2ac432b6c7662da0e894272831be9f7f18182901/src/promptCell.ts#L220-L350) loops through every preceding **code** model for source, with no metadata inclusion check; its prior AI history pass uses prompt/answer widgets. Its [notebook setup](https://github.com/AnswerDotAI/ai-jup/blob/2ac432b6c7662da0e894272831be9f7f18182901/src/index.ts#L183-L225) adds a prompt button, not a per-cell context control. The existing [research note](ai_jup_research_and_design.md) describes those semantics. This is evidence about that inspected commit, not a claim that no fork or later version can add such a control.

## Verification needed before shipping

1. Unit-test the pure mode resolver on first/middle/last prompt positions, 0/1/10 boundaries, moves, deletion, new cells after Custom selection, and duplicated/legacy IDs. Assert current prompt/current answer exclusion and complete-pair history versus independently selected AI source behavior.
2. Unit-test metadata inheritance and migration, including old notebooks with no flags, old AI cells, notebook defaults unchanged, and tool declarations retained despite prose exclusion. Test server/transport counts separately from character-budget omissions.
3. Browser-test every cell type in a real notebook, save/reload, offscreen/windowed scroll, two open notebooks with copied cell IDs, rapid mode changes, keyboard edit/command interactions, and no duplicate checkboxes/listeners. Assert actual box visibility and height rather than only `selectOption`/`check` success.
4. Browser-test a prompt using cells above and below, a moved answer, an unsaved edit, and a below AI turn. Inspect the actual backend payload/context event so the mode and checkbox display cannot disagree with submitted context. Confirm AI output/source never gains checkbox markup and no selected cell silently becomes an executable tool.

Feasibility: the frontend UI and durable metadata are supported by public JupyterLab 4.6.4 model/widget APIs. The harder work is defining coherent selection semantics and extending the server request/context assembler for below cells, Custom, linked AI turns, and inherited tools. No runtime code was changed for this assessment.
